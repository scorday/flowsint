# AVL4: backend-авторизация и проекты

Это первый реализованный этап [плана интеграции](avl4-integration-plan.md).
Подключение `main_panel`/SDK реализовано в [frontend-этапе](avl4-frontend.md).
Backend передачи карточек реализован в [этапе 5](avl4-card-transfer.md).
[Действие Monitoring](avl4-monitoring.md) реализовано и проверено локально.
Конфигурация развёртывания и живая сквозная приёмка остаются этапом 7.
Самостоятельный frontend использует собственный JWT; режим AVL4 — общую панель и SDK.

## Режим запуска и зависимости

`FLOWSINT_AUTH_MODE=avl4` включает интеграцию. Режим по умолчанию — `standalone`;
любое другое значение считается ошибкой конфигурации. API и Celery-воркеры
одной интегрированной установки должны запускаться в режиме `avl4`.

Клиент Auth устанавливается отдельно поверх стандартного окружения. Для
`requirements-avl4.txt` требуется настроенный приватный индекс AVL4; его адрес,
учётные данные и секреты не записываются в этот документ или Git.

```sh
uv sync --all-packages --group dev
uv pip install -r requirements-avl4.txt
```

После установки дополнительного клиента команды этого окружения выполняются
через `uv run --no-sync`: повторный обычный `uv sync` может вернуть зависимости
из основного standalone-lockfile; после него нужно повторить установку
`requirements-avl4.txt`. Упаковка отдельного интегрированного образа относится
к этапу первоначального развёртывания.

Подключение Auth задаётся поддерживаемыми клиентом переменными `AUTH_REDIS_*`.
Это отдельная конфигурация от `REDIS_URL` очереди Flowsint. Все обращения к
сессиям, пользователям и проектам выполняет публичный Auth-клиент.

На стороне Auth добавлены настройки `APPS_FLOWSINT` и
`APPS_FLOWSINT_BASE_URLS`. По умолчанию адреса пусты, приложение не появляется
в меню работающих окружений. Настройка адресов и выдача доступа выполняются
при отдельном авторизованном развёртывании.

## Контракт запроса

- Сессия: `c-avl-session` либо `h-avl-session`, проверяемая Auth-клиентом.
- Проект: обязательный `h-avl-project`, как в платформенном SDK AVL4.
- Пользователь определяется по сессии, а не по `h-avl-user`, телу запроса или
  локальному JWT. Cookie выбранного проекта не используется.
- Запросы с cookie, изменяющие данные, требуют `Origin` из `ALLOWED_ORIGINS`.
- Отсутствующая/недействительная сессия: `401` и маркер
  `X-AVL-Auth-Guard: session-rejected`.
- Нет заголовка проекта: `400 PROJECT_REQUIRED`.
- Нет актуального доступа к приложению/проекту: `403`, без маркера потери сессии.
- Ошибка соединения с Auth или отсутствие установленного клиента: `503`,
  без внутренних подробностей и без маркера потери сессии.

Самостоятельные регистрация, выдача JWT, редактирование локального профиля,
поиск пользователей и управление участниками расследований возвращают `404`.
`GET /api/auth/me` возвращает идентичность Auth; проект для него также обязателен.

## Данные и права

Каждому расследованию и другим данным Flowsint назначаются `project_id` и
аудитный `created_by`. Любой пользователь с доступом к проекту может работать
со всеми его расследованиями, графами, чатами, flows, шаблонами, типами и ключами.
Создатель не получает исключительных прав. Локальные `Profile` и записи ролей
для пользователей AVL4 не создаются; старые таблицы остаются для standalone.

SQLAlchemy-контекст ограничивает ORM-запросы текущим проектом, проверяет записи
и принадлежность родительских объектов. Новые записи получают проект и аудит
на сервере. Перемещение между проектами, прямой SQL и bulk insert/update
в интегрированном контексте запрещены; изменения выполняются через проверяемые
ORM-объекты. Bulk delete также ограничивается проектом.

Перед обращением к Neo4j принадлежность графа проекту проверяется в SQL.
Операции со связями ограничивают оба конца выбранным графом; свойства запроса
не могут перезаписать серверный `sketch_id`. Динамические метки и типы связей
проверяются и экранируются, карты свойств передаются параметрами.

Пакетный логгер сохраняет контекст проекта вместе с событиями и восстанавливает
его в потоке записи. События разных проектов записываются отдельными транзакциями.

Legacy-строки относятся к `__standalone__` и недоступны проектам AVL4.
Standalone-запросы не читают проектные строки AVL4; изменение загруженной
проектной строки в standalone-контексте также отклоняется.

Ключи инструментов шифруются с контекстом проекта и доступны его пользователям
через Vault-сервис. Чужой проект не получает ключ по известному ID.

Celery-сообщения содержат проект, инициатора и контекст его личного проекта,
если он имеется; session cookie в очередь не попадает. Воркер повторно проверяет
актуальный доступ и принадлежность графа перед выполнением, а также доступ
перед SQL-записями и обращениями к Neo4j. Сообщение без контекста не выполняется
на AVL4-воркере; AVL4-сообщение не выполняется на standalone-воркере.

Для SSE/AI-потоков доступ повторно проверяется перед очередной отправкой,
если с предыдущей проверки прошло минимум 10 секунд. При потере доступа
или недоступности Auth передача прекращается. Уже выполненные внешние действия
не отменяются автоматически; атомарность между PostgreSQL, Neo4j и внешними
инструментами не гарантируется.

## Схема и проверка

Добавлена Alembic-ревизия `d3e4f5a6b7c8` после `c7d1f0a92b3e`.
Для новой установки используется обычная последовательность миграций.
Downgrade не удаляет проектные данные молча: при наличии строк AVL4 он
отклоняется. Миграция не применялась к работающим базам.

Проверки запускаются из соответствующего подпроекта с тестовыми настройками
БД/очереди. Основные наборы:

```sh
# flowsint-core/
uv run --no-sync pytest tests/repositories tests/services tests/tasks -q

# flowsint-api/
uv run --no-sync pytest tests -q

# avl4-auth/ в репозитории AVL4
make test
```

`test_avl4_policy.py` использует реальные публичные DTO и адаптер Auth с
подменой сетевых вызовов. Если дополнительный клиент не установлен, этот файл
пропускается; для проверки интеграции его необходимо установить. HTTP-проверки
используют SQLite и подмену Auth-транспорта; живые Auth/Redis/PostgreSQL/Neo4j
и реальный брокер относятся к последующей сквозной приёмке.
