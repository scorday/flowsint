# Общий граф расследования

Реализация общего графа расследования. Проверки и границы проверенной среды
перечислены в `investigation-graph-verification.md`.

## Модель

Расследование владеет сущностями и направленными типизированными связями. Схема
(`Sketch`) остаётся SQL-объектом расследования и задаёт выбранное представление
его графа. Границы расследований и проектов сохраняются.

В Neo4j:

- `GraphScope.key` — составной ключ проекта и расследования, сериализованный
  однозначно. Запись Scope блокируется на время транзакции изменения графа.
- `GraphEntity.uid` — постоянный внутренний UUID. Предметные идентификаторы,
  отображаемая метка и атрибуты не заменяют этот UUID.
- `GraphEntity.identity_keys` — нормализованные предметные ключи. VK использует
  числовой user ID; разрешённый через VK короткий адрес связывается с этим ID.
  Противоречащие числовые ID вызывают конфликт, а не автоматическое слияние.
- `GraphView` соответствует SQL-схеме. Отношения `SHOWS` задают её состав узлов
  и хранят координаты, флаг, размер, форму, цвет и прочие настройки отображения.
- Связи между сущностями хранят общий UUID, тип, атрибуты и `view_ids` — состав
  схем, где связь показана. Два видимых узла не означают автоматического показа
  всех связей между ними. Для отдельных событий поддерживается `event_key`
  (например, хеш транзакции).
- Предыдущие конфликтующие значения сохраняются в `graph_history`, вместе с
  источником изменения и временем. Это наблюдения, а не автоматическое признание
  одного из значений достоверным.

Имена людей и названия организаций не являются ключами идентичности.
Неопределённые сущности создаются отдельно; повторное использование явно
выбранного существующего объекта сохраняет его UUID. Человек и его аккаунт —
разные типы сущностей. Для ручного объединения доступны общие операции графа,
переносящие появления и типизированные связи.

При передаче данных через очередь внутренний ID переносится в служебном
`_graph_uid` и восстанавливается в приватный атрибут FlowsintType. Он не заменяет
поле `SocialAccount.id`. Любой такой ID разрешается только внутри проверенного
расследования и доступной схемы.

## Поведение

- Обогащение записывает сущности и связи в расследование и показывает результаты
  только на схеме запуска. Состав остальных схем сохраняется.
- Изменения общих свойств видны при загрузке всех схем, показывающих сущность.
  Клиент обновляет данные также при возврате фокуса в окно.
- «Убрать со схемы» меняет только состав представления. Удаление самой схемы
  также не удаляет общий граф.
- «Удалить из расследования» требует прав удаления и удаляет объект со всех
  схем вместе с его связями. Это отдельная команда с описанием последствий.
  Данные сохраняются как tombstone. Повторное явное наблюдение того же
  предметного объекта может вернуть его в граф; это не механизм запрета сбора.
  Удалённые схемы и расследования закрываются для поздних записей уже запущенных
  задач, даже если задача получила доступ до удаления.
- «Объекты расследования» позволяет добавлять уже существующие узлы и отдельно
  выбирать показываемые связи. «Схема из выделенного» создаёт представление
  выбранных узлов и видимых связей между ними.
- Ручная форма, включая VK, и быстрое добавление проверяют общий граф до записи.
  При совпадении устойчивого идентификатора предлагают использовать существующий
  объект или показать его, если он уже на схеме. Общие атрибуты при этом не
  перезаписываются, существующая раскладка сохраняется; соседние связи не добавляются.
  Для имени без устойчивого ключа показываются только кандидаты того же типа
  (подстрока без учёта регистра, от трёх символов, до 20 результатов). Пользователь
  может выбрать кандидата или создать отдельный объект; автоматического слияния
  по имени нет. При ошибке проверки создание блокируется до повтора или возврата
  к редактированию. После записи загружается серверный граф, чтобы ответ с уже
  существующим UUID не оставил визуальный дубликат временного узла.
- Перенос схемы в другое расследование запрещён. Для другого расследования
  нужен явно проверенный импорт, а не изменение родительского ID.
- Прямой пользовательский Cypher через GraphService запрещён: он обходил бы
  границы расследования. Обогащение криптотранзакций использует общий репозиторий.
- SQL-записи AVL4 материалов и операций по-прежнему отражают импорт в конкретную
  схему (wire contract v1 не меняется), но их проекции в графе общие в пределах
  расследования и идентифицируются по исходной карточке. Старый повтор операции
  не должен заменять более свежий общий снимок.

## API

Обычный ответ графа сохраняет `nds` / `rls`, но ID — внутренние UUID, а не
Neo4j elementId. Идентификаторы Neo4j из старых ссылок сохраняются как алиасы.

- `GET /api/sketches/{id}/graph` — представление схемы.
- `GET /api/sketches/{id}/investigation-graph` — общий граф её расследования.
- `POST /api/sketches/{id}/nodes/matches` — проверка кандидата `GraphNode` без
  записи, с правом изменения схемы. Возвращает до 20 объектов с `match`
  (`exact` / `possible`) и `on_sketch`. Scope берётся из проверенной SQL-схемы.
- `POST /api/sketches/{id}/subgraph` — добавить `node_ids` и `edge_ids` на схему.
  Выбранные связи включают свои конечные узлы.
- `DELETE /api/sketches/{id}/nodes` и `/relationships` — убрать со схемы.
- `DELETE /api/sketches/{id}/investigation-elements` — удалить `node_ids` /
  `edge_ids` из расследования.
- `POST /api/sketches/create` принимает необязательные `node_ids` / `edge_ids`
  общего графа целевого расследования.

Scope разрешается через SQL-схему с действующими проверками доступа к проекту.
Поля scope из тела запроса отбрасываются. Запрос другого проекта или ссылки на
чужие сущности не дают доступа к чужому графу.

## Миграция и восстановление

Новый код требует graph schema constraints. Совместное использование старых
записей со `sketch_id` и новых GraphEntity запрещено. Миграция не выполняется
автоматически при запуске API.

Перед разрешённым применением оператор должен:

1. Остановить запись API и workers в отдельном согласованном окне. Этот документ
   не является разрешением на остановку сервисов или развёртывание.
   До обновления завершить или отменить согласованным способом старые задания
   очереди: сообщения прежней версии не несут `_graph_uid` для объектов без
   предметных ключей. Не смешивать старые workers с новой моделью графа.
2. Сохранить согласованный полный backup PostgreSQL и Neo4j и исходный release.
   Для Community Neo4j использовать штатный offline `neo4j-admin database dump`;
   проверить восстановление дампа на отдельном экземпляре. JSON-архив ниже —
   дополнительная копия записей расследования, не замена полного backup.
3. Настроить подключения в приватном окружении оператора. Не передавать пароли
   в аргументах команд и не включать конфигурацию в отчёты.
4. Запустить dry-run для каждого явно выбранного расследования:

   ```sh
   uv run python -m flowsint_core.core.graph.migration \
     --project PROJECT_ID --investigation INVESTIGATION_UUID
   ```

   Для standalone использовать `--project __standalone__`. Неизвестное
   расследование или несовпадающий проект отклоняются, включая пустые расследования.

5. Принимать только проверенный результат. Противоречащие VK ID, неверный проект
   и связи через границу расследования блокируют миграцию для ручного разбора.
6. Для применения указать новый путь приватного архива (существующий файл не
   перезаписывается; права файла 0600):

   ```sh
   uv run python -m flowsint_core.core.graph.migration \
     --project PROJECT_ID --investigation INVESTIGATION_UUID \
     --backup /PRIVATE_BACKUP_DIR/investigation-before.json --apply
   ```

   Транзакция заново сверяет источник с архивом перед изменением и отменяется,
   если он изменился. Все изменения одного расследования атомарны в Neo4j.
   Повторное применение после успеха не дублирует данные.
   Затем отдельная SQL-транзакция перепривязывает `Avl4Material.node_id`, результаты
   операций импорта, структурированные ссылки в logs/scans/chats/analyses.
   Предметные `id` и свободный текст доказательств не переписываются. Исходные
   SQL-значения входят в приватный архив.
   Если Neo4j уже применён, а SQL-фаза завершилась ошибкой, сохранить оба архива
   и повторить команду с **новым** путём `--backup`: старые UUID/elementId остаются
   алиасами и позволяют восстановить mapping узлов и связей без дублей.
7. Сверить количество объектов и связей, состав каждой схемы, координаты,
   историю конфликтов, старые ссылки и операции AVL4. Проверить права другого
   проекта. Только затем разрешать запись обновлённому приложению.

При ошибке транзакции исходные записи остаются в Neo4j. При необходимости отката
уже применённого изменения остановить запись и восстановить согласованные
полные дампы Neo4j/PostgreSQL и исходный release. Не запускать старый код поверх
нового графа и не пытаться восстановить старые elementId обычным CREATE из JSON.
Штатный `dump/load` Neo4j может поменять UUID базы внутри `elementId`. До запуска
старого приложения проверить и перепривязать SQL-ссылки с помощью кода этой версии:

```sh
uv run python -m flowsint_core.core.graph.migration \
  --project PROJECT_ID --investigation INVESTIGATION_UUID \
  --backup /PRIVATE_BACKUP_DIR/investigation-before.json --restore-references
# После успешного dry-run:
uv run python -m flowsint_core.core.graph.migration \
  --project PROJECT_ID --investigation INVESTIGATION_UUID \
  --backup /PRIVATE_BACKUP_DIR/investigation-before.json --restore-references --apply
```

Этот режим читает существующий архив и не мигрирует граф. Он требует точного
совпадения scope, количества записей, всех меток/свойств, типов и концов связей,
а также исходного SQL-снимка (либо уже исправленного снимка при повторе).
Совпадения числовой части ID недостаточно. Несовпадение останавливает операцию;
нельзя обходить его ручной заменой UUID в SQL. При восстановлении другой версией
Neo4j, меняющей также номера записей, потребуется отдельный проверенный разбор.
После восстановления проверить состав схем и данные до возобновления записи.

Несколько прежних копий одной уверенно распознанной сущности на одной схеме
объединяются в одно появление. Все прежние раскладки сохраняются в
`SHOWS.migration_layouts`, исходные записи — в `migration_records`; активная
раскладка выбирается детерминированно по порядку старых ID. Экспорт схемы
включает выбранный подграф, а не скрытую часть расследования. Общие API графа
сохраняют существующий предел 100 000 узлов; диалог показывает первые 200
совпадений фильтра по загруженному графу. Для более крупных расследований
понадобится отдельная серверная пагинация.

Старая версия оставляла tombstones в Neo4j после удаления SQL-схемы. Если схема
уже отсутствует в SQL, установить её расследование без внешних доказательств
невозможно: такие архивные записи сохраняются отдельно и не переносятся по
догадке. Они недоступны через новый граф и не блокируют общую readiness.
Для существующих SQL-схем миграция сохраняет также их удалённые записи.

## Проверки

```sh
REDIS_URL=redis://127.0.0.1:6379/0 uv run pytest flowsint-core/tests
uv run ruff check flowsint-core/src flowsint-core/tests
cd flowsint-app
npm run test
npm run typecheck
npm run build
```

Интеграционные сценарии требуют отдельной временной Neo4j 5.26 с выключенной
аутентификацией, слушающей **только loopback** на Bolt-порту 17687. Нельзя
использовать рабочую базу. Тесты активируются переменной
`FLOWSINT_TEST_NEO4J_URI=bolt://127.0.0.1:17687` и удаляют только созданные ими
случайные scope. Без этой переменной они пропускаются; Python job CI запускает
временную Neo4j и включает их. Тестовый экземпляр после проверки остановить.
